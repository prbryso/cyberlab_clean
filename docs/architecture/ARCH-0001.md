**Document ID:** ARCH-0001

**Status:** Draft

**Author:** Phillip Bryson

# Purpose

The Educational Object Model defines the fundamental abstractions that make up Systems Studio.

Rather than designing Systems Studio around user interface screens, Flutter widgets, or individual lessons, the platform is designed around educational concepts.

The objective is to create a reusable educational engine capable of teaching any systems-oriented subject.

Cybersecurity is the first implementation of this architecture.

It is not the architecture itself.

---

# Philosophy

Systems Studio is based upon one fundamental principle:

> **Teach the System, Not Just the Rule.**

Traditional educational software often presents information as a sequence of pages or lessons.

Systems Studio instead models the subject itself.

Learners explore systems.

Lessons explain systems.

Simulations demonstrate systems.

Assessments evaluate understanding of systems.

Everything begins with the educational model rather than the user interface.

---

# Design Principles

The Educational Object Model follows several core principles.

## Educational First

The architecture represents educational concepts.

It does not represent Flutter widgets or screens.

---

## Domain Independent

Nothing within the engine understands cybersecurity.

The engine understands only educational concepts.

Cybersecurity, Artificial Intelligence, Physics, Electronics, Communications, and Control Systems all become educational domains built upon the same engine.

---

## Reusable

Educational objects should be reusable whenever possible.

A diagram, lesson, simulation, glossary, or assessment should be capable of appearing in multiple learning paths without duplication.

---

## Extensible

New educational domains should require little or no modification to the engine.

New domains register themselves rather than modifying existing engine code.

---

## Separation of Responsibilities

The engine owns educational behavior.

Educational domains own subject matter.

The user interface owns presentation.

Each layer has a single responsibility.

---

# Educational Hierarchy

The Educational Object Model is organized as follows.

```
EducationalDomain
│
├── LearningModule
│       ├── Lesson
│       ├── SystemModel
│       ├── Diagram
│       ├── Simulation
│       ├── Assessment
│       ├── Reference
│       └── Glossary
│
└── LearningPath
```

Each object represents an educational concept rather than a software implementation.

---

# Core Objects

## EducationalDomain

Represents a major field of study.

Examples include:

- Cybersecurity
- Artificial Intelligence
- Control Systems
- Electronics
- Physics
- Communications
- Software Engineering

A domain contains one or more learning modules.

---

## LearningModule

A Learning Module represents a major topic within a domain.

Examples include:

Cybersecurity

- Password Security
- Phishing
- Encryption
- Multi-Factor Authentication

Control Systems

- Feedback
- Stability
- PID Controllers

Each module contains lessons, diagrams, simulations, assessments, and other educational assets.

---

## Lesson

A Lesson teaches a single concept or learning objective.

Lessons should be relatively small, focused, and reusable.

Examples include:

- What is Hashing?
- Dictionary Attacks
- Salt
- Rate Limiting

Lessons become the fundamental instructional building blocks of the platform.

---

## SystemModel

A System Model represents how something works.

Rather than describing isolated facts, a System Model captures the components, relationships, behavior, and interactions within a system.

Examples include:

- Password Authentication
- Email Delivery
- Public Key Infrastructure
- TCP/IP Communication
- PID Control Loop

System Models represent the central educational concept within Systems Studio.

---

## Diagram

A Diagram provides a visual representation of a System Model.

Diagrams should eventually support:

- Multiple perspectives
- Zooming
- Layering
- Animation
- Interactive exploration

A single System Model may have multiple diagrams.

---

## Simulation

A Simulation demonstrates system behavior.

Rather than simply displaying information, simulations allow learners to observe how systems behave over time.

Examples include:

- Password attacks
- Authentication flow
- Network communication
- Firewall operation
- Control system response

Simulations reinforce systems thinking through experimentation.

---

## Assessment

Assessments measure understanding.

Assessments may include:

- Knowledge checks
- Interactive scenarios
- Design exercises
- System analysis
- Problem solving

The emphasis is understanding systems rather than memorizing facts.

---

## Reference

References provide supporting information.

Examples include:

- Standards
- Publications
- Books
- Articles
- External resources

References supplement instruction without interrupting learning flow.

---

## Glossary

The glossary defines important terminology.

Terms should be reusable across multiple modules.

Definitions should remain consistent throughout the platform.

---

## LearningPath

A Learning Path defines a recommended sequence through educational material.

Different learning paths may exist for:

- Beginner
- Intermediate
- Advanced
- Administrator
- Engineer
- Instructor

Learning Paths organize existing educational assets without duplicating content.

---

# Relationships

The engine understands relationships between educational objects.

Examples include:

A Learning Module contains Lessons.

Lessons may reference multiple System Models.

System Models may contain multiple Diagrams.

Diagrams may support multiple Perspectives.

System Models may contain multiple Simulations.

Assessments may evaluate one or more Lessons.

Learning Paths organize Lessons into meaningful sequences.

---

# Educational Registry

All educational objects are registered with the Systems Studio engine.

The registry provides discovery rather than hardcoded navigation.

The registry becomes the authoritative catalog of:

- Domains
- Modules
- Lessons
- System Models
- Simulations
- Diagrams
- Assessments
- References
- Glossary Terms

---

# Future Direction

The Educational Object Model is intentionally independent of any specific technology.

Flutter is the current implementation platform.

Future implementations may target web, desktop, mobile, virtual reality, augmented reality, or other educational environments.

The Educational Object Model should remain stable even as presentation technologies evolve.

---

# Summary

The Educational Object Model provides the conceptual foundation of Systems Studio.

Rather than organizing software around pages or screens, Systems Studio organizes knowledge around educational concepts.

This architecture enables reusable educational assets, domain independence, interactive learning, and long-term extensibility.

Every future enhancement to Systems Studio should reinforce this model rather than bypass it.

Ultimately, Systems Studio is not intended to teach cybersecurity.

It is intended to teach complex systems.
